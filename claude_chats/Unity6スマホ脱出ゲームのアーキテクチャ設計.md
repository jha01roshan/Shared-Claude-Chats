## Assistant

脱出ゲームのような「データ間の参照関係が多く、後から仕様が膨らみやすい」ジャンルでは、ご提示の3観点はすべて「**定義元を一つに絞り、文字列IDの手打ちをなくし、ロジックをViewから剥がす**」という一つの方針で同時に解けます。まず全体像を示してから各層を説明します。

## 採用する基本方針

データ駆動 + 単一状態(Single Source of Truth) + リアクティブ更新 + ロジック/MonoBehaviour分離、の4点セットです。脱出ゲームの本質は「フラグとアイテムの状態に応じて、表示画像とタップ領域の挙動が変わる」だけなので、状態を一箇所に集約し、それ以外は全部そこから導出される(派生)構造にするのが最も壊れにくくなります。

以下、各層の設計判断と、それがご提示の3観点にどう効くかを説明します。

## 1. マスターデータ層 — 参照を「文字列ID」でなく「型付き参照」にする

脱出ゲームでヒューマンエラーが最も多く出るのは「`flag_door_open` のような文字列IDの打ち間違い・コピペずれ・リネーム漏れ」です。これを構造的に潰すため、アイテム・フラグ・視点・条件などをすべて ScriptableObject アセットとして定義し、相互参照はインスペクタ上のオブジェクト参照（ドラッグ＆ドロップ）で持たせます。

これだけで次が保証されます。存在しないものは参照できない（アサインの有無で検出できる）、リネームしても参照が壊れない、そのアセットがどこで使われているかをエディタから追える。文字列の手打ちが消えるので、二重管理とタイプミスの両方が同時になくなります。

## 2. パズルを「コード」ではなく「データ」として表現する

脱出ゲームのロジックは突き詰めると「ある条件が満たされたら、ある結果を起こす」だけです。これを条件（フラグ値・所持アイテム・現在視点のAND/OR）と結果（フラグ更新・アイテム増減・視点遷移・SE再生）の組み合わせとしてデータ化します。Unityなら `[SerializeReference]` を使って条件ツリーを多態的にインスペクタで組めるようにしておくと、新しいパズルを足すときも「既存データには一切触れず、条件クラスを一種類追加するだけ」で済みます。これが仕様変更を最小工数にする中心的な仕掛けです。ロジックがコードに散らばらないので、変更の影響範囲が「そのデータ1件」に閉じます。

## 3. ランタイム状態を `GameState` ひとつに集約する

実行時に変化する真実（フラグの値・所持品・現在の視点）を `GameState` という単一オブジェクトだけが持ちます。それ以外の表示や判定は、すべてここから導出される派生情報として扱います。「同じ事実を2か所が持っていて、片方の更新を忘れて食い違う」というバグの大半は、状態を一箇所に絞るだけで消えます。セーブ／ロードもこの1オブジェクトをシリアライズするだけになり、保存漏れが起きません。

## 4. リアクティブ更新 — Viewは状態を購読するだけ

タップ → コマンド発行 → `GameState` を更新 → 変更通知 → 各Viewが反応、という一方向の流れにします。各MonoBehaviourが状態のコピーを抱えたり、毎フレーム自前で条件チェックしたりするのを禁止すると、表示と内部状態がずれません。`R3`（旧UniRx）や軽量なイベントバスで十分です。

## 5. ロジックとMonoBehaviourの分離 — テストで人為ミスを早期に潰す

状態・条件評価・コマンド処理は `UnityEngine` に依存しない純粋C#として書き、Unity Test Framework でユニットテストします。MonoBehaviourは「画像を差し替える」「タップ座標をコマンドに変換する」程度の薄いアダプタに留めます。パズルの解法ロジックを実機やプレイ通しに頼らず机上で検証できるので、ヒューマンエラーがリリース前に落ちます。

## プリレンダー画像・モバイル固有の注意点

画像は重いので Addressables で管理し、メモリ常駐を視点単位で制御します。ホットスポット（タップ領域）は、実際のプリレンダー画像をエディタ上に重ねて矩形を描けるカスタムエディタを用意すると、座標の手打ちずれという典型的ミスがなくなります。画像のパスを手で文字列指定せず、視点定義SOにアセット参照として持たせるのも同じ理由です。セーブデータだけはSO参照を直接書けないため、各定義に「自動生成した不変ID（手打ちGUIDではなく自動採番）」を1つ持たせ、保存時のキーにします。テキストはUnity Localizationパッケージのキー参照に寄せれば、多言語も定義元が一箇所に保てます。

## 補足（過剰設計の回避）

少人数・小規模なら、上記をフルスタックのDIコンテナやECSで武装する必要はありません。「SOをデータの定義元にする・状態を1つに集約する・ロジックをViewから剥がす」の3点さえ守れば、観点はほぼ達成できます。逆に企画者がスプレッドシートでマスターを管理したい場合は、スプレッドシートを唯一の定義元として、そこからSOとenumを自動生成するインポータを噛ませます。ただしパイプラインの保守コストが増えるので、チーム規模とのトレードオフで選ぶのがよいです。

## Assistant

公平な指摘で、その通りです。永続化を「単一状態の設計から自動的に導かれる副産物（＝GameStateを1個シリアライズするだけ）」と見なして、モバイル注記の中に押し込めてしまいました。実際には永続化は前回の設計判断に逆向きの圧力をかける一級のテーマで、独立して設計すべきでした。なぜ一級かというと、次の2点が他の層に制約を課すからです。

ひとつは、前回「型付き参照（SO参照）でヒューマンエラーを潰す」と推したことと真っ向から衝突する点です。SO参照はそのままディスクに保存できません（再起動後はインスタンスが別物になり同一性が保てない）。つまり保存のためには各定義に安定したIDが要り、そのID採番ルール（不変・再利用禁止）は実行時やオーサリング全体に効く制約になります。前回これを「自動採番のID」と一行で済ませましたが、本来はここが設計の起点でした。

もうひとつは、モバイルアプリは更新され続けるため、旧バージョンのセーブを新バージョンで読む必要があり、スキーマ移行（マイグレーション）が永続化の中心課題になる点です。これは後付けできず、最初のID設計とデータ形式を縛ります。

整理すると、永続化の境界は次のようになります。
```
This block is not supported on your current device yet.
```

以下、永続化を一級のテーマとして設計し直し、最初の3観点に紐づけて述べます。

## 1. 保存形式は「定義のミラー」にしない（二重管理の回避）

最も犯しやすい設計ミスは、`GameState` をそのまま写した保存用DTOを別に定義することです。これをやるとフラグを1つ足すたびに「定義・実行時・保存DTO」の3か所を更新する羽目になり、まさに二重（三重）管理になります。

避け方は、保存データを「全フィールドのミラー」ではなく「立っているフラグのID／所持アイテムのID／現在視点のID＋その値」という最小の差分として持つことです。これは定義集合から自動的に導出される形なので、新しいフラグやアイテムを定義として足しても保存スキーマのコードは一切変わりません。保存・復元のロジックは「定義を列挙してIDと値を読み書きする」汎用処理一本になり、項目ごとの分岐が消えます。これが仕様変更時の工数を最小化する勘所です。

## 2. 安定IDは「手打ちさせない・絶対に再利用しない」

セーブとオーサリングの安全性を両立させる鍵が、各定義に持たせる安定IDの運用ルールです。IDは新規アセット作成時に自動採番（GUID等）し、人間に打たせません（タイプミスというヒューマンエラーの除去）。そして一度発行したIDは、定義をリネームしても変えず、定義を削除しても二度と別の意味で再利用しません。再利用すると、旧セーブの「フラグ7=ON」が新バージョンで別のフラグを誤って立ててしまうからです。この「不変・再利用禁止」は永続化が他層に課す制約で、最初に決めておかないと後から直せません。

## 3. マイグレーション耐性を前提に読む

更新で項目が増減しても旧セーブが壊れないよう、復元は寛容に行います。具体的には、保存ファイルにあるIDを定義集合へ照合し、現存しないID（削除された項目）は黙って無視し、保存ファイルにない新規IDは初期値（未取得・フラグOFF）として扱います。加えて保存データ自体に `schemaVersion` を持たせ、必要なときだけ明示的な変換関数を順に適用します。これにより、追加・削除程度の仕様変更ならマイグレーションコードを書かずに吸収でき、構造を変える変更だけにバージョン変換を限定できます。

## 4. モバイル特有の保存タイミングと耐障害性

スマホはプレイ中に着信・バックグラウンド化・OSによる強制終了が日常的に起きます。したがって明示セーブではなく、状態変更のたびのオートセーブを基本にします。書き込みは「一時ファイルに全量書き出してからリネームで置き換える」原子的書込にし、書き込み途中でアプリが殺されてもファイルが半端な状態にならないようにします。万一読込に失敗した場合は直前の正常セーブ（バックアップ世代を1つ保持）へフォールバックし、壊れた状態で起動しないようにします。保存先は `Application.persistentDataPath`、必要に応じて iCloud / Google Play Saved Games でのクラウド同期や複数スロットを別途検討します。

## 5. 改ざん耐性は要件次第

一人用のパズルゲームなので優先度は低めですが、課金や実績が絡むなら、保存データにチェックサムや軽い難読化を施し、外部編集を検出して弾く程度の対策を入れます。これはセキュリティというより「サポートに来る壊れたセーブの切り分けを楽にする」目的が大きいです。

まとめると、永続化を後回しにできない理由は「型付き参照と安定IDのトレードオフ」「ID不変・再利用禁止という全体制約」「マイグレーションという継続的要件」の3つが、いずれも他の層の設計を先に縛るからです。前回はここを副産物扱いしたのが誤りでした。

## Assistant

正直に言うと、二つの別々の問題が混ざっていて、その混同自体が問題でした。

まず「JSON を選んだ理由」そのものは、移行コードを手で書くときやサポートで壊れたセーブを調査するときに人間が読めて助かる、という可読性のためで、書き込み頻度の主張と突き合わせて妥当性を検証しないまま既定値として選んでいました。そこは詰めが甘かったです。

ただ、ご指摘の前提――「JSON が低速だから、頻繁なオートセーブと両立しない」――は、このゲームの負荷に対しては実はほぼ当たりません。脱出ゲームの `GameState` はフラグ数十〜百程度＋数個のアイテム＋現在視点で、数KBです。この規模を `JsonUtility` 等でシリアライズするコストはサブミリ秒で、形式を JSON からバイナリに替えても体感は変わりません。つまり「JSON だから遅い」を理由に形式を差し替えるのは、間違った場所を最適化することになります。

「状態変更のたびに保存」で本当にコストになるのは、シリアライズのCPUではなく次の3つです。ディスク書き込みのフラッシュ遅延（temp書き出し＋リネームの原子的書込は毎回ファイル全量を書き直し、フラッシュは端末次第で数ms〜数十msかかる）、文字列確保によるGCスパイク（毎タップ走ると描画がカクつく）、そしてメインスレッドを同期で塞ぐこと。いずれも形式の問題ではなく、保存頻度とディスク書き込み頻度を直結させてしまったことが原因です。

## 本当の誤りは「オートセーブ」の意味の取り違え

「状態変更のたびのオートセーブ」という表現が不正確でした。意図すべきだったのは「プレイヤーに明示的なセーブ操作を要求しない」であって、「フラグが立つたびにディスクへ fsync する」ではありません。正しい設計は、保存頻度とディスク書き込み頻度を切り離すことです。

具体的には、状態変更は即座にメモリ上の `GameState` を更新して dirty フラグを立てるだけにします（プレイヤーから見た「保存」は常に瞬時）。ディスクへの書き出しは、短いデバウンスタイマー（最後の変更から数百ms〜数秒）と、ライフサイクルイベントでまとめて行います。モバイルで効くのは後者で、`OnApplicationPause(true)` / `OnApplicationFocus(false)` はアプリがバックグラウンドへ回るときに発火し、OSはプロセスを殺す前にこの通知を出すので、ここで確実にフラッシュすれば「強制終了で状態を失う」は防げます。つまり毎タップでディスクを叩く必要はそもそもなく、バックグラウンド化の瞬間を捉えれば十分です。書き込み自体はスナップショットを取って別スレッド／ジョブで原子的に行い、メインスレッドのカクつきを避けます。

## そのうえで形式をどう選ぶか

この切り離しさえできれば、形式は速度ではなく別の軸で選べます。JSON は可読性で移行とデバッグが楽なので、この規模なら妥当な選択です。将来セーブが肥大化したりGC確保が無視できなくなれば、ソースジェネレータ方式のバイナリシリアライザ（MessagePack 等。リフレクション不使用・低確保）に替えると、サイズと確保量が減ります。さらに保存が大きく高頻度になり「全量書き直し」が重くなる段階まで来たら、WALを持つ組み込みDB（SQLite等）で差分を耐久的に追記する方式へ上げます。ただし数KBの脱出ゲームのセーブにこれらは過剰で、現時点では「JSON＋デバウンス＋ライフサイクルでの非同期フラッシュ」が素直です。

要するに、形式選択を無検証で済ませたのは事実として詰めが甘かったですが、修正すべき本体は形式ではなく、保存頻度とディスク書き込みを直結させた点でした。

## Assistant

保存される形式を JSON にする理由としての「可読性」が弱い、という点には同意します。ただ二点、切り分けさせてください。

まず可読性の価値は「読み書きが正しいことの一度きりの確認」には尽きません。効くのは運用中に繰り返し起きる場面です。脱出ゲームはプレイヤーが詰まって問い合わせてくる典型ジャンルで、「扉が開かない」「アイテムが消えた」という報告に対し、送られてきた(あるいはクラウドから引いた)セーブを開いて `flag_door_unlocked: false / inventory: [key]` と読めれば状態が即座に分かります。更新のたびに書くマイグレーションコードを実際の旧セーブと突き合わせて検証するときも、QAが「最終部屋の直前のセーブ」を手で作って特定パズルへ飛ぶときも同じで、いずれも一度きりではなく更新のたびに繰り返されます。なので「一度動作確認すれば十分」という括りは、そこだけは違います。

とはいえ結論としてはあなたに寄ります。これらの恩恵は「永続化される形式」が JSON である必要がありません。必要なのは「人間が見たいときに JSON として見られること」であって、保存はバイナリのまま、同じDTOをオンデマンドで JSON にダンプする経路を一本用意すれば足ります。デシリアライズのコードはどのみち手元にあるので、それを呼んで吐き出す十数行のツールを一度書くだけ。「バイナリ保存＋必要時にJSONダンプ」で両取りでき、保存形式を JSON のままにしておく理由はやはり弱い。ここは認めます。

一方で、バイナリを採る理由として挙げられた「オートセーブの処理負荷を下げる」の方は、この規模では同じくらい弱いです。前回述べた通り、数KBのセーブではシリアライズのCPUも書き込みバイト数も誤差で、オートセーブの実コストはフラッシュ遅延とメインスレッド占有が支配的です。そしてそれは形式ではなく、デバウンス＋別スレッドでの原子的書込＋ライフサイクル(`OnApplicationPause`)でのフラッシュという構成で解く問題で、JSONかバイナリかとは独立です。「速いシリアライザを入れればオートセーブ負荷が下がる」を主軸に据えると、すでに構成側で解いた問題を別の場所でもう一度解こうとすることになります。そこは置き換えになっていません。

では結局どちらか——バイナリでいいです。ただし理由は速度ではありません。本当に効く差は二つ。ひとつはアロケーションで、ソースジェネレータ方式のシリアライザ(MessagePack-CSharp 等)はリフレクションを使わずほぼ無確保で動くため、前回挙げた実コストの三つ目であるGCスパイクの軸に効きます。これはオートセーブを頻繁に回すほど地味に効く。もうひとつはサイズと、副次的なカジュアル改ざん耐性で、JSONは誘うように編集できてしまい、編集で壊れた状態の問い合わせがサポートコストになります。可読性は前述のダンプ経路で温存できるので失うものもない。

実装上の注意を一点。iOS の Unity は IL2CPP なので、リフレクション依存のシリアライザはAOTで壊れやすく、MessagePack を使うならソースジェネレータ／AOTコード生成が前提です。それと移行耐性については一つ後退があります。JSONは未知・欠落フィールドに寛容で、数手前に強調したマイグレーション耐性と相性が良い。バイナリでその寛容さを保つには、キー付き(map型)契約＋バージョンフィールドという規律が要ります。MessagePackのkeyed contractならほぼ維持できますが、タダではない点は申し添えておきます。

まとめると、行き先(バイナリ保存)には同意しますが、その理由は「オートセーブ高速化」ではなく「低アロケーションとサイズ、軽い改ざん耐性」であり、可読性は捨てるのではなくオンデマンドのJSONダンプへ移す、というのが正確な判断だと思います。

ご指摘の通りで、Unity・C# でパフォーマンス志向の保存をするなら MemoryPack が自然な選択です。MessagePack を口にしたのは慣れによる既定で、より速い選択肢に照らして正当化していない——この会話で繰り返している同じ癖です。MemoryPack は MessagePack-CSharp と同じ作者（neuecc）が出した後発のシリアライザで、MessagePack より数倍〜数十倍速い。VarInt やタグといったエンコード処理を行わず、C#のメモリ配置をできるだけそのままコピーするゼロエンコード設計が速さの理由で、標準オブジェクトで数倍、構造体配列ではさらに桁違いに速く、Unity 対応もあります。

ただ一点だけ、流れに乗ったまま正確にしておきます。これまで合意してきた通り、数KBの保存をデバウンス＋別スレッドで書くこの用途では、シリアライズのスループットは律速ではありません。なので「MemoryPack は速い」を採用理由の主軸に据えるのは厳密には筋が違う。ここで本当に効くのはゼロエンコードゆえのほぼ無確保という性質で、以前挙げた三つの実コストのうち GC の軸に効きます。つまり選ぶ理由は「速いから」ではなく「確保が少ないから」。ここは一貫性のために崩しません。

トレードオフも一つ。MemoryPack はクロス言語標準ではなくC#固有フォーマットで、int は常に4バイト固定のため int 主体のデータでは MessagePack より大きくなることもあります（逆に float や Vector3 は小さい）。自己完結したセーブではどちらも問題になりません。

マイグレーションについては、以前話した「追加・削除に寛容」を MemoryPack で得るには明示が要ります。既定はメンバの宣言順に並べるシーケンシャルで、デシリアライズ時にメンバ順を変えることはできません。既定の限定的なバージョン耐性はメンバ追加のみを許し、他の変更は制限されるため、スキーマを動かすなら完全なバージョン耐性モードを使います。具体的には `GenerateType.VersionTolerant` を指定すると、明示的に上書きしない限りレイアウトは自動的に Explicit になり、`[MemoryPackOrder]` で順序を固定します。MessagePack の文字列キー契約より順序の規律はやや厳しいですが、順序を付け忘れるとコンパイルエラーで気づける（こっそりバグにならない）ので、むしろ最初に掲げたヒューマンエラー予防には合致します。

まとめると、MemoryPack に替えるべき、という点に同意します。ただし理由はスループットではなく低確保（GC）で、保存互換のために VersionTolerant ＋ 明示順序を設定する、というのが正確なところです。
